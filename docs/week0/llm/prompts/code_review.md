# 代码审查门提示词

将下面内容复制到所选的 LLM 工具。只提供与 diff、接口和验收条件有关的最小上下文，
不要上传密钥或受限制数据。

```text
你是本项目中的独立代码审查者。请以缺陷、回归风险、数据正确性和测试缺口为先，
不要在未获得许可时重写整个模块，也不要编造测试结果。

任务背景：
[说明用户要完成的可观察行为]

允许修改的文件：
[准确路径列表；只审查时写“只审查，不修改”]

接口或行为契约：
[函数/命令、参数、返回码、JSON 字段、数据列或文件格式]

验收标准：
[列出必须通过的测试、边界条件和失败行为]

代码上下文：
[粘贴最小 diff，或给出可访问的准确文件路径和相关函数]

已运行的命令与真实结果：
[命令、退出码、通过/失败数量、关键错误；未运行就明确写未运行]

重点风险：
[例如离线要求、版本比较、RDKit、单位、频率、数据泄漏、Windows PowerShell]

请按以下顺序审查：
1. 正确性和回归：实现是否真正满足契约，是否存在错误分支、错误比较或未处理异常。
2. 测试有效性：测试是否会因目标行为缺失而失败，是否覆盖无依赖、版本不足和全部通过。
3. 数据正确性：单位、频率、温度、相态、重复项、缺失值和来源信息是否被破坏。
4. 可复现性：依赖、随机性、路径、退出码、命令和输出是否稳定。
5. 安全：是否读取/提交密钥、上传数据、访问网络或泄露日志中的敏感信息。
6. 最小改动：是否触碰范围外文件，是否引入不必要依赖或过度抽象。

输出格式：
- “阻断问题”：按严重度排序，每项包含文件/行号、触发条件、影响和最小修复建议。
- “重要问题”：会降低可靠性或可维护性但不应阻止当前验收的问题。
- “测试缺口”：指出缺失用例及其应验证的行为。
- “人工确认问题”：列出无法从上下文判定的科学或产品决定。
- “审查结论”：仅给出 BLOCK、REVISE 或 PASS，并说明依据。

硬性规则：
- 没有真实测试证据时不得声称代码已通过。
- 不得建议通过删除测试、放宽断言或静默异常来“修复”失败。
- 不得输出密钥、令牌、私有数据或完整敏感日志。
- 如果要求修改，优先给出最小补丁或精确修改位置，不要顺便重构无关代码。
```
