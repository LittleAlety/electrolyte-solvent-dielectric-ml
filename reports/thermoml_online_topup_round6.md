# ThermoML 在线补抓（第六轮）：本地存档已死，而刷新买到的新化合物是 0 个

**日期：** 2026-09-25
**探针：** `probes/thermoml_online_topup_probe.py`
**汇总：** `probes/thermoml_online_topup_summary.json`
**测试：** `tests/test_thermoml_online_topup_probe.py`（43 项，全离线可跑）
**状态：** closed。本轮只做测量，不向任何数据集单元写入一个数值。

本轮回答两个问题：**本地那份 189 MB 的 ThermoML 整包还能不能救**，以及**重新从 NIST 抓一遍能多买到几个化合物**。
答案是：救不回来；而且**一个都买不到**。

---

## 0. 结论（先给答案）

1. **本地 tgz 救不回来。** 189,433,115 字节里 95.6% 是 0 字节，头尾全 0、不是 gzip 成员；唯一真实载荷是
   120–128 MiB 处的一个 8 MiB 块。这是被零填充的中断写入 / 预分配文件，不是压缩流，重读多少遍都一样。
2. **刷新要花约 0.7–1.0 GB（估计）。** 全库 11,923 条记录，按实测每条 62–85 KB 外推，约 740 MB–1.0 GB；
   若只取介电切片则只要约 7–11 MB（走带引号的短语查询，实测）。旧的 ~189 MB 整包 `.tgz` 已经不存在（404）。
3. **刷新能买到的新化合物是 0 个。** 严格口径（纯组分 / 液相 / 零频）在线共 **103** 个，与本地
   `dielectric_raw.csv` 里同一个门槛下的 **103** 个**逐键完全相同（集合相等，差集为空）**。
   相对 246 个化合物的 v1.0 数据集多 **0** 个，相对 308 键全名录多 **0** 个。
4. **因此档案刷新不是 v1.x 覆盖率的杠杆。** 覆盖只能靠**新来源**，不能靠重爬 NIST——
   本地缓存已经是 NIST 介电数据的**完整快照**。
5. **两个可迁移的教训**，都在下面单独成节：
   - **单词查询陷阱**（§5）：裸单词严重欠返，多词短语严重过返，拿它们给语料"称重"会得到错的规模感。
   - **Component 内联 InChIKey 塌缩**（§4）：这一条把 headline 从"1 个新化合物"改成了"0 个"，是本轮最值得记住的坑。

## 1. 本地 tgz 还能救吗：不能

测量对象 `data/raw/thermoml_archive/ThermoML.v2020-09-30.tgz`（探针实测）：

| 量 | 实测值 |
| --- | ---: |
| 文件大小 | 189,433,115 字节（约 189.4 MB） |
| sha256 | `984a6f658988a5cc38322f72ffecf32ca1a29de4ec9ff0884f6e7681552cc807` |
| 头 32 字节 | 全 `0x00` |
| 尾 32 字节 | 全 `0x00` |
| 零字节 | 181,073,438（95.6%） |
| 非零字节 | 8,359,677（**4.4%**） |
| 首个非零偏移 | 125,829,120（= 120 MiB） |
| 末个非零偏移 | 134,217,727（= 128 MiB − 1） |
| gzip 魔数 / tar 魔数 | 无 / 无 |
| 判定 | `zero_filled`，`salvageable = false` |
| 旁挂 manifest | 无（`manifest_expected_size = null`） |

**为什么不能救：** 唯一一段非零数据是偏移 125,829,120..134,217,727 的**恰好** 8,388,608 字节（正好 8 MiB），
落在 120–128 MiB 这一整块里，其余 95.6% 全为零。一个真正的 gzip 流不可能以 120 MiB 的零字节开头。
这是**先按最终大小预分配、写到 128 MiB 处被中断、剩余空间保持零填充**的典型签名。缺的不是"再解压一次"，
而是那约 181 MB 的内容本身——它从未落盘。旁边没有 sidecar / manifest 可以校正大小，即使有也没用：
内容不在文件里。**结论：这个 tgz 是死文件，应记为损坏并另行取源。**

判据写在 `classify_archive_payload` 里，顺序是硬性的：magic 优先，零前缀一律判 `zero_filled`，
**任何非 gzip 载荷都不可能被判成 `ok_*`**；这条由测试把守。

## 2. 刷新要花多少字节

静态目录已经下线，所以"刷新"只能等于"查 JSON API"。下表每一行都是探针 `online.queries` 的**实测**记录
（`bytes` 为实际传输字节，`size` 为命中记录数）：

| 查询 | 类型 | 命中记录 | 传输字节 | 每记录 |
| --- | --- | ---: | ---: | ---: |
| `*`（`pageSize=1`） | 总数 | 11,923 | 6,050 | — |
| `permittivity` | 裸词 | 117 | 8,154,069（8.15 MB） | 69.7 KB |
| `dielectric` | 裸词 | 93 | 7,400,459（7.40 MB） | 79.6 KB |
| `"Relative permittivity at zero frequency"` | 短语 | 47 | 2,915,794（2.92 MB） | 62.0 KB |
| `"Relative permittivity at various frequencies"` | 短语 | 49 | 4,160,991（4.16 MB） | 84.9 KB |
| `"Relative permittivity"` | 短语 | 109 | 7,840,073（7.84 MB） | 71.9 KB |

本轮请求预算 **11/40**，`bytes_transferred` 合计 **30,477,436 字节（约 30.5 MB）**。

**全库刷新成本（估计，不是实测）。** 真正下全 11,923 条要分页拉取，规模 = 11,923 × 每记录字节：

- 按 62.0 KB/记录 ≈ **740 MB**；按 71.9 KB/记录 ≈ **857 MB**；按 84.9 KB/记录 ≈ **1.0 GB**。
- 这一项标成**估计**：我们没有真的把 11,923 条全部拉下来称重，只对少数查询实测了每记录字节再外推。
- **介电切片才是真正要花的钱：约 7–11 MB（实测量级）。** 要走的就是上面三条短语查询，
  它们直接命中结构化属性名，合计不到全库的 2%。
- 旧的 ~189 MB 整包 `.tgz` 路线**不可用**（404，见 §5）。

## 3. 刷新能买到多少新化合物：0 个

口径分层，严格程度从高到低（全部来自 `probes/thermoml_online_topup_summary.json`）：

| 口径 | 在线 | 本地名录 | 新增 |
| --- | ---: | ---: | ---: |
| **严格**：纯组分 + 液相 + 零频 ε | **103** | 103（同门槛） | **0** |
| 严格口径 vs v1.0 数据集（246 化合物） | 103 | 246 | **2** |
| 宽口径：出现在任一介电记录里的 InChIKey | 320 | 308 | 133 |

表里第二行的 **2** 需要解释清楚，否则会读成"多买到 2 个"：在线严格口径里有 **2** 个键
（`IAHFWCOBPZCAEA-UHFFFAOYSA-N`、`XEZNGIUYQVAUSS-UHFFFAOYSA-N`）不在 v1.0 的 246 个化合物里。
但这 2 个**本来就在本地的 `dielectric_raw.csv` 抽取里**，只是当初没有被收进 v1.0——它们是**内部准入决策**，
不是新数据。所以对"本地名录"的差集仍然是 **0**。**严格口径的 103 与本地同门槛的 103 是同一个集合**：探针把在线短语查询（47 + 49 + 109 条记录）按
"1 个组分 + 液相 + 零频"抽出的 InChIKey 集合，与 `dielectric_raw.csv` 里
`property_family == zero_frequency`、`is_pure == True`、`phase == Liquid` 的
`primary_inchi_key` 集合做差集，**两个方向都为空**。

也就是说：**NIST 在线档案里的零频介电化合物，本地缓存一个不缺、也一个不多。**
本地缓存就是这份数据的完整快照，重爬 NIST 在化合物覆盖上**严格零收益**。

**为什么这一条可信（而不是"没搜到就当没有"）：** 编排者独立核对过，`dielectric_raw.csv` 里全部
**44** 个不同的零频 DOI 都能被在线查询命中，**0 漏**。所以在线索引是本地缓存的**真超集**，
"0 个新化合物"是**索引确实没有**，而不是**我们没问到**。

**宽口径的 133 个不要当收益。** 它们大多只是摘要里出现"dielectric / permittivity"措辞、
或是混合物组分、或频率依赖（非零频）的记录，**不是**可用的零频 ε 观测。两个口径**不可混用**。

**这个 0 对 v1.x 的意义：** 与化合物覆盖学习曲线的读数一致——混合表示的 R² 在 60 个化合物时为 **0.216**、
到 236 个化合物才到 **0.364**，且在这个量级上每加一个化合物边际仍为正
（见 `reports/dielectric_compound_coverage_curve.md`）。覆盖的瓶颈是**化合物数量**，
而重爬 NIST 的边际是 0——**coverage 来自新来源，而不是重爬 NIST**。

## 4. 一个把 headline 从 1 改成 0 的坑：Component 内联 InChIKey 塌缩

这一节是本轮最值钱的部分，因为它直接推翻了**本轮自己的第一版结论**。

第一版提取器从数据集的 `Component` 节点直接读 `sStandardInChIKey`，得出
"在线严格口径 29 个化合物，其中 1 个（磷酸 `NBIIXXVUZAFLBC-UHFFFAOYSA-N`）是新的"。

这个 29 和这个 1 **都是假的**。反证很直接：单独取记录 `10.1021/je101184s`，
本地抽到的是 **27** 个不同化合物，而第一版提取器在整条记录上只产出 **1** 个不同键。

**根因：** 这条记录的 `Compound` 表有 27 个不同化合物，但**每一个数据集的
`Component` 节点都重复写着第一个化合物的 `sStandardInChIKey`**。
NIST 的 JSON 序列化把每个 Component 的内联键都塌缩到了 `Compound[0]`。
于是"直接读内联键"会把一项 27 个分子的研究，悄悄记成一个分子——**并且不报错**。

**可靠的指针**是 `RegNum/nOrgNum` 计数器和 `path: "/Compound/<n>"` 路径，本地抽取走的正是这条。
修正后：

- 单条 `10.1021/je101184s`：**1 → 27** 个不同键；
- 全库严格口径：**29 → 103**；
- 新增化合物：**1 → 0**（磷酸那个"新化合物"是塌缩造出来的幻影，磷酸既不在本地 103 里、
  也不在在线 103 里——它本来就不该出现在这个集合里）。

提取器现在**优先用指针解析**（`nOrgNum` → `/Compound/<n>`），
只有在记录根本没有 Compound 表时才回退到内联键；三条回归测试把这个行为钉住：
多化合物记录必须解析出**不同**的键、无 `RegNum` 时按 `path` 解析、无表时回退内联键。

**可迁移教训：** 处理 NIST ThermoML JSON 时，**数据集的 Component 内联 InChIKey 在记录含多个化合物时不可信**；
必须走 `RegNum` / `path` 指针。而这类错误**不会抛异常**，只会安静地少算——
所以"化合物数对不上本地"这种对账信号必须当真，它正是发现这个坑的入口。

## 5. 网络允许了什么、挡了什么（明写）

- **静态站点变成了 SPA。** `https://trc.nist.gov/ThermoML/` 返回 200，但它已经不再是一个静态文件目录，
  而是一个 JavaScript 单页应用；旧的"列目录 / 直接下包"路径不复存在。
- **旧入口全部 404。** `ThermoML.v2021-03-31.tgz`、`ThermoML.bib`、`ThermoML_Data.xml`
  三个 HEAD 实测均 **404**（逐条记在 summary 的 `failures` 里）。~189 MB 的整包路线因此**不可用**。
- **活的入口是 JSON API：** `https://trc.nist.gov/ThermoML-API/objects?query=<词>`，HEAD / GET 均 200。
  单条记录入口 `/objects/20.5000.trc.thermoml/<doi>` 也可用（注意：它返回的是**记录本身**，
  不再套一层 `content`）。**没有 XML 输出模式**（带 `Accept: application/xml` 仍回 JSON），
  所以在线侧必须用 JSON 走查，不能直接复用本地的 XML 解析器。
- **限流：** 本轮 11/40 请求，未触发 429；但这是有礼貌客户端（预算上限、单次 60 s 超时）下的结果，
  小额抽样不能保证全量分页时不被限流。
- **查询语义陷阱（容易踩）：** 这个索引像**短语索引**，行为与一般全文检索相反：
  - **裸单词严重欠返回。** `permittivity` 只回 **117** 条、`dielectric` 只回 **93** 条——
    远小于真实相关记录数（对比 `dielectric` 93 条 vs `dielectric constant` **1,850** 条，
    单词竟然是短语的子集都不到）。
  - **多词短语严重过返回（不带引号的多词查询）。** 编排者实测：`dielectric constant`（**不带引号**）→ **1,850**（105.7 MB）、
    `static permittivity`（不带引号）→ **1,610**、`relative permittivity`（不带引号）→ **1,238**。
    这些命中大多是摘要 / 混合物里的措辞，远多于严格相关的几十条。
  - **对比：同一批词的带引号精确短语反而收敛得很准**，直接瞄准结构化属性字段：
    `"Relative permittivity"` → 109、`"Relative permittivity at various frequencies"` → 49、
    `"Relative permittivity at zero frequency"` → 47。headline 只用这一档。
  - **取语料规模用 `query=*` + `pageSize=1`**，只花 6 KB 就能拿到 11,923 这个总数，
    不必分页。
  - **可迁移教训：** 面对这种索引，单词查询只能当"有没有"的探针，**绝不能**当计数或规模的依据。
- **索引是超集（正面证据）：** 见 §3 的 44/44 覆盖检查——0 漏，所以在线索引是本地缓存的真超集。

## 6. 局限

- **API 索引是全文 + 短语式的，不是结构化字段查询。** "某查询里没有"**不等于**"语料里没有"。
  本轮缓解证据是 44/44 覆盖检查，但它只覆盖**本地已知的 44 个零频 DOI**，
  不能推广到"所有 NIST 零频记录都在线可查"。
- **"0 个新化合物"是相对本地名录而言的。** 若本地名录本身漏了某个化合物、而它同时又没被这三条短语查询
  命中，本轮的 0 就看不到它。这是"超集 + 同门槛集合相等"能给出的最强结论，但它不是绝对证明。
- **宽口径（320 / 133）不是覆盖收益。** 含措辞命中、混合物组分与频率依赖记录，两者不可混用。
- **全库与切片字节数是"部分实测 + 外推"。** 单条查询的传输字节是实测；
  "全库 ~0.74–1.0 GB"是从每记录字节外推的**估计**，未真的整包下载称重。
- **本轮没有拉取任一在线 ε(T) 数值进正文核对。** 所有"新化合物"判定只到 InChIKey 与 DOI 级别，
  数值本身仍待在后续流程里逐条核验。
- **单次运行的网络状态不代表长期状态。** 本轮未触发限流；这不保证可复现，旧站点 / 接口的可用性由对方决定。
